# Ретроспектива agy-ревью: фикс MONITORING (8 кругов)

Дата: 2026-10-16. Задача: `docs/exec-plans/completed/2026-10-16-fix-monitoring-sheet-growth.md`.
Отчёты: `docs/drafts/agy_monitoring_sheet_growth_review.md` (последний круг).

## Почему потребовалось 8 кругов

1. **У ревьювера нет памяти между кругами.** Каждый запуск `agy` — новый процесс, который
   заново оценивает весь дифф и не знает, какие замечания уже разобраны и отклонены.
   Отклонённые P3 возвращались в следующих кругах, иногда уже как P2.
2. **Дифф менялся между кругами.** После каждого принятого замечания менялись сигнатуры
   (`FakeGSpreadWorksheet.update`), перемещались тесты, добавлялись файлы. Ревьюер каждый раз
   видел новую поверхность и находил новые мелочи.
3. **ТЗ не фиксировало технические факты до 5-го круга.** Только после ложного P1 про
   «дефицит больше 100 строк» в ТЗ были добавлены проверенные по исходникам gspread факты
   (`len(col_values(1)) <= row_count`), после чего P1 исчез.
4. **Критерий сходимости («нет нового реального P2») не выполним, когда ревьювер
   переквалифицирует отклонённую вкусовщину в P2.** Формально почти каждый круг давал P2.

## Противоречия между кругами

1. **`max(100, rows_missing)` vs фиксированные `add_rows(100)`.**
   - Круг 3: показал, что тесты с `row_count=1` и 100+ строками данных воспроизводят
     физически невозможное состояние, → производство упрощено до `add_rows(100)`.
   - Круг 4: P1 — «захардкожено 100, нужно `max(100, rows_missing)`».
   - Круг 6: P2 — снова «нужно `max(...)`».
   - Круги 7–8: P2/P3 — «`max(...)` — мёртвая ветка, уберите, верните фиксированные 100».
   Итог: оставлен `max(...)` как дешёвая защита и ветка покрыта тестом.
2. **Тип исключения в фейке.**
   - Круг 3: P2 — «`ValueError` нарушает контракт, бросайте `GSpreadException`».
   - Круг 4: P2 — «`GSpreadException` недостаточно, нужен `APIError`».
   Итог: `APIError` (подкласс `GSpreadException`, удовлетворяет оба замечания).
3. **Синхронизация `row_count` с данными в конструкторе фейка.**
   - Круг 5: P3 — «`row_count` может быть меньше числа строк данных, синхронизируйте через `max`».
   - Круг 8: P3 — «та же синхронизация мешает тесту, поэтому пришлось мутировать свойство вручную».
   Итог: синхронизация оставлена, искусственная мутация задокументирована комментарием.
4. **Тест защитной ветки >100.**
   - Круг 4 («чего не хватает»): добавить тест на дефицит >100.
   - Круги 7–8 («что упростить»): удалить этот тест как проверяющий невозможный сценарий.
5. **Расположение self-тестов фейка.**
   - Круг 5: перенести из `test_update_report.py`.
   - Круг 6: перенести в `tests/test_protocol_fakes.py`.
   - Круги 7–8: ок, но файл должен быть явно перечислен в плане/коммите.
6. **Рефакторинг `FakeAgcClient`.** Замечание «добавь `open_by_key` и переиспользуй общий фейк»
   повторялось в кругах 2, 3, 5 и 6, но каждый раз отклонялось: локальные фейки в тесте
   проще и не трогают общий фейк роутерных тестов.
7. **Write-through в `FakeGSpreadWorksheet.update`.** Круги 5 и 8: «фейк не мутирует `_data`,
   поэтому тест не проверяет сквозную запись» — оба раза отклонено: для проверки фикса
   достаточно перехвата вызовов, а полноценная эмуляция листа усложняет фейк.

## Что улучшить в процессе

1. Вести файл «принятые/отклонённые замечания» и передавать его в ТЗ следующего круга либо
   добавлять в ТЗ готовый список `resolved/rejected` — это гасит повторные P2/P3.
2. Сразу выносить в ТЗ проверенные контракты библиотек (как факт про `col_values`), чтобы
   ревьюер не строил на них ложные P1.
3. Между кругами менять дифф только по принятым P1/P2, не рефакторить тестовую обвязку —
   иначе каждый раунд получает новую поверхность для замечаний.
4. Ограничить цикл 3 кругами: дальше останавливаться и выносить неразрешённые P2/P3 на
   решение владельца.
