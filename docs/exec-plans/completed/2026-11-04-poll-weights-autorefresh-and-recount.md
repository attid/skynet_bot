# 2026-11-04-poll-weights-autorefresh-and-recount: авто-пересчёт весов при создании опроса + `/poll_recount`

## Контекст
- Взвешенное голосование (`routers/polls.py`, `cq_join_list`) хранит накопленную сумму весов в
  `my_poll["buttons"][i][1]` и список проголосовавших имён в `buttons[i][2]`.
- `/poll_reload_vote` обновляет веса в `voting_service` и в БД (`BotValueTypes.Votes`), но уже
  сохранённые суммы в опросах не пересчитывает. Участники, проголосовавшие до reload, остаются
  с прежним весом, а при отмене голоса (`sum -= new_weight`) возникает дрейф, т.к. вычитается
  не то значение, которое прибавлялось.
- Решения владельца продукта:
  1. Опрос, созданный из поста канала (`channel_post`) или командой `/poll`, должен начинаться
     с **актуальных** весов: пересчёт весов выполняется в момент создания опроса.
  2. Индикация работы — реакция (`👀` → `👌` / `⚠️`) на исходном сообщении (пост в канале или
     команда в чате), по которому создаётся опрос.
  3. Список ненайденных пользователей **никогда** не отправляется в канал: только в личку
     `MTLChats.ITolstov` (`84131737`), без конфигурируемости.
  4. Дополнительно — ручная команда `/poll_recount` для уже существующих опросов: ответ на
     пересланное в админ-чат сообщение бота с кнопками, либо аргумент-ссылка
     (`t.me/<name>/<id>`, `t.me/c/<internal>/<id>`).
  5. «Осиротевшие» участники (имя в списке есть, веса больше нет) остаются в списке с вкладом 0
     и перечисляются в отчёте.
- Стоимость пересчёта признана незначительной: Grist развёрнут на том же сервере, поэтому
  cooldown, кэш `name_list` и параллельный резолв **в эту задачу не включаются**. Horizon
  вызывается один раз на уникальный адрес (максимум 3 адреса из `chat_to_address`).
- Жёсткий инвариант: **флаг `my_poll["closed"]` никогда и ни при каких условиях не изменяется**.
  Закрытые опросы не пересчитываются вовсе.
- Вне задачи: устаревшее чтение `forward_from_chat`/`forward_from_message_id` в `/poll_close`
  (Bot API 7+ эти поля не присылает) — отдельный тикет.

## Риски и открытые вопросы
- Опрос появляется с задержкой на время пересчёта (Horizon + Grist); индикация — реакция `👀`.
  Таймаут 30 с: по истечении опрос создаётся на текущих весах, админ получает предупреждение.
- Пересчёт на каждом создании опроса пишет `BotValueTypes.Votes` в БД чаще, чем раньше — принято.
- Пересчёт меняет видимые цифры открытых опросов задним числом; для `/poll_recount` это явное
  действие админа, отчёт «было → стало» обязателен.
- Участники с изменённым `@username` не находятся в весах → вклад 0 (существующая проблема
  резолва по имени, вне этой задачи).
- `bot.edit_message_text` может упасть для старых сообщений канала — пересчёт всё равно сохраняется.
- Для чатов, отсутствующих в `chat_to_address`, весов нет — `/poll_recount` отказывается.
- Дрейф, накопленный до этой задачи, сам не откатывается: он исчезает при пересчёте, т.к. сумма
  считается из списка имён. Для старых опросов нужен явный `/poll_recount`.

## Верификация
- Сценарий A: публикуем опрос в канале → на посте появляется `👀`, затем `👌`; сообщение с
  кнопками сразу содержит актуальные цифры и `Need 50(75) из 100`; ненайденные приходят в личку.
- Сценарий B: опрос открыт → `/poll_reload_vote` меняет веса → переслать сообщение бота в
  админ-чат → `/poll_recount` в ответ → отчёт «было → стало», в канале обновлены цифры и кнопки.
- Сценарий C (инвариант): закрытый опрос → `/poll_recount` отказ; `closed` и содержимое опроса
  не изменяются ни при каких условиях.
- Тесты: `tests/routers/test_polls.py::test_poll_autorefresh_*`, `::test_poll_recount_*`.
- Логи: `logger.info` с chat_id, message_id, до/после по опциям, списком обнулённых и результатом
  обновления сообщения.

## Пост-ревью (внешний ревьювер `agy`, 19 раундов до сходимости)
Отчёт последнего раунда: `docs/drafts/agy_poll_weights_review.md`. По итогам ревью дополнительно сделано:
- `_publish_weighted_poll` — общий публикатор: экранирование HTML в вопросе, `Need …` сразу в первом
  сообщении, `save_poll(None, …)` (немедленный коммит, чтобы клик по кнопке не увидел «пустой» опрос),
  удаление опубликованного сообщения, если запись в БД не удалась, уведомление админа с id чата.
- `cmd_save_votes` — лок перенесён внутрь (защищает и `/poll_reload_vote`), таймаут на оба входа,
  итерация только по уникальным адресам, тримминг имён из Grist, `NEED` для нулевой суммы.
- `_render_poll_view` — общий рендер, используется и в `cq_join_list` (убран рассинхрон экранирования),
  бюджет длины текста, лимит 64 символа на кнопку, сохранение индексов `callback_data` при битых опциях.
- `_recalculate_button_weights` — нормализованные имена пишутся обратно в `button[2]` (иначе старый голос
  нельзя отменить), дедуп внутри опции, отчёт «было → стало» + обнулённые.
- `/poll_recount` — ключ из forward/reply/ссылки (в т.ч. `t.me/s/`, `t.me/c/…`, темы, кавычки, скобки,
  ссылки в `entities`/`caption_entities`, регистронезависимо), отказ при битых/закрытых опросах,
  `save_poll` до `edit_message_text`, обработка `message is not modified` и любых ошибок редактирования.
- Тесты: `tests/routers/test_polls.py` (87 тестов), `tests/fakes.py` (fake `load_poll` теперь повторяет
  поведение реального сервиса).

Отклонено с обоснованием: перенос `session` в `cmd_save_votes(None, …)` уже сделан; claim «idle-сессия
middleware держит соединение БД» неверен (`async_sessionmaker` не берёт соединение до первого запроса);
`MessageOriginChat` не содержит `message_id`, поэтому пересылка из групп не может дать ключ опроса —
вместо этого в отказе команды добавлена подсказка использовать ссылку; cooldown/TTL и проверка
«свежести» весов не вводятся (решение владельца).

Открытые вопросы владельцу: суммировать ли веса нескольких signer-ключей одного `@username`
(сейчас перезапись — поведение исходного кода); запуск `/poll_recount` во время активного голосования
может потерять клик, сделанный в момент пересчёта (нет optimistic locking в `load_poll`/`save_poll`).
