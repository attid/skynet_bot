# vote-xdr-multi-tx-packing: точный расчёт операций и упаковка в несколько транзакций

## Контекст
- Прошлый шаг (`vote-xdr-skip-noop-ops`) убрал пустые операции, но остался грубый предохранитель
  `MAX_VOTE_OPERATIONS = 80`, взятый «из расчёта, что больше 20 подписантов на счёт не бывает».
  При 100+ реальных операциях остаток аккаунтов молча не попадал в XDR, а лишние операции
  вообще не нужны — после отсечения no-op их число заранее известно.
- Лимит Stellar — 100 операций на транзакцию. Требования владельца:
  1) считать точное число операций заранее;
  2) не разрывать один аккаунт между транзакциями (все его изменения — в одной);
  3) докладывать так, чтобы в каждой транзакции было не больше 100 операций;
  4) при нескольких транзакциях отдавать их файлом, где у каждой следующей sequence на 1 больше.

## Риски и открытые вопросы
- Транзакции должны отправляться **по порядку**: sequence зашит в XDR. Если какую-то отклонить,
  остальные не пройдут (sequence gap) — это ожидаемо и отражено в сводке бота.
- Верхняя граница операций одного аккаунта — `max_count(20) подписантов + 1 SetOptions`, то есть
  21; 100-операционный лимит на транзакцию при этом не достигается никогда за счёт одного
  аккаунта, поэтому `ValueError` — защита на будущее (например, при росте `max_count`).
- Комиссия: каждая транзакция оплачивается отдельно (base fee × число операций).
- `plan_account_vote_ops` по-прежнему делает один Horizon-запрос на аккаунт (async), поэтому
  время сборки линейно растёт с числом multisp-аккаунтов; при необходимости можно распараллелить
  с ограничением конкурентности.

## Верификация
- Прод: `/get_vote_fund_xdr` — при изменениях приходит файл `vote_fund_xdr.txt` с K строками,
  сводка «Обновлено аккаунтов: N, транзакций: K (подписывать по порядку, sequence уже +1)».
  Декод каждой строки должен содержать только реально изменённые аккаунты и ≤100 операций.
- Локально: `uv run pytest -q`, `uv run ruff check .`, `uv run ruff format --check .`.
